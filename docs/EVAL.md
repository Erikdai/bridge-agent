环境：Windows 11，DeepSeek `deepseek-chat`（无视觉、无 json_schema），Playwright 自带 Chromium，步数上限 25（第一轮）/ 40（之后）。运行期间机主在同一台电脑上使用微信、Edge 和 Outlook，前台焦点频繁被抢，所有数字都是在这种真实干扰下测得的。命令：`bridgeagent eval`。

## 几点诚实的说明

- 这是 8 个任务、每个任务 1 到 3 次运行的小样本，用来说明机制是否成立，不是统计意义上的成功率。
- 验证调用只看回放后的观察摘要，摘要里缺信息就会误判“未完成”，第二轮的 print 和 notepad 就是这样。修复后信息更全，但这一层判断仍然是整个链路里最弱的环节。
- 技能里除了下载目录之外的值仍是写死的，页面数据一变就只能靠验证失败后重学，参数化在路线图里。
- settings-lookup 第二轮里模型用 PowerShell 查主机名绕过了设置应用，判定通过但不符合任务精神，说明自动判定应该检查过程而不只看结果。
- 机主全程在用这台电脑。焦点守卫因此被充分测试，但也意味着同一任务不同轮次之间的差异有一部分来自环境。

原始数据在 `runs/eval-*/results.json`，每一步的观察和决策在对应 `runs/<时间戳>/trace.jsonl`。

## Bridge 指标：确定性场景矩阵（`scripts/bridge_matrix.py`，不用 LLM）

针对“程序能确定路由，不代表执行一定可复现”这个质疑，六个场景全部脚本化，每个都在真机上验证了一次（2026-10-15）：

| 场景 | 要确认的事 | 结果 | 细节 |
|---|---|---|---|
| DOM → UIA → DOM | 同一会话里自动切换并继续 | 通过 | browser → desktop → browser，计算器显示 6,912 |
| Chrome 内嵌对话框 | 打印预览路由到 d 引用并经 UIA 关闭 | 通过 | 21 个对话框节点，目标打印机 Microsoft Print to PDF，Cancel 走 UIA |
| 别的浏览器抢焦点 | 观察前被另一个 Chromium 抢前台 | 通过 | 焦点守卫把 agent 的窗口拉回，观察到的是自己的页面 |
| 观察后、执行前被抢焦点 | 按键不能敲进别人的窗口 | 通过 | 执行器先核对句柄并拉回计算器，999 出现在计算器显示上 |
| 技能跨环境回放 | 不用 LLM 完成网页到计算器 | 通过 | 3 步全跑完，trail 里读到 6,912 |
| MCP 连续调用 | 线程亲和与状态不乱 | 通过 | 40 次 observe/press 交替调用，0 错误，33.5 s |

补充的防线：桌面点击在没有 UIA 模式可用、退化为鼠标坐标点击时，也会先核对观察时的窗口句柄。

### 反向用例（同一脚本，第二次运行）

| 场景 | 期望 | 结果 | 细节 |
|---|---|---|---|
| 观察后目标窗口被关闭 | 拒绝动作，按键不泄漏到别的窗口 | 通过 | 执行器报“观察到的窗口已不存在”，页面输入框保持为空 |
| 观察后 UIA 元素失效 | 安全失败，不盲目点击 | 通过 | 旧元素无可用模式，退化到坐标点击前核对窗口失败，返回错误 |
| 目标窗口无法重新激活 | 返回明确错误，不发键鼠事件 | 通过 | 模拟激活被拒，返回“focus was taken”，页面输入框保持为空 |
| 观察后窗口被移动 | 按引用点击仍然命中 | 通过 | 不存坐标，UIA 实时取元素位置，显示变为 1 |

十个场景全部通过，脚本可重复运行，建议作为回归测试。
